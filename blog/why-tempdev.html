Building TempDev: Zero-Dependency Disposable Cloud Environments

2026.05.20

I recently wrapped up a core side project: TempDev (also known as Container Provider). It is a web application that spins up fully functional, isolated Linux development environments in your browser in under 500ms. There is no signup, no credentials overhead, and zero user friction.

Why I Built It

The genesis of TempDev lies in another project of mine, Rta, an AI-assisted code editor client. Rta is designed to analyze and run generated script loops. To run agent-generated code safely, I needed a way to isolate running scripts without compromising the host machine.

I looked into existing cloud sandbox solutions. The available options were either too heavy, resource-hungry, locked behind API paywalls, or required complex account registration. For a developer side project, spending massive monthly fees on a Kubernetes setup or cluster VMs was not viable. I wanted a container provider that was minimal, fast, and could run efficiently on a single cheap host instance.

Under the Hood: The Architecture

To keep the system extremely fast, I built it with Go. The backend runs on a single AWS Free Tier t3.micro instance. It orchestrates local Docker containers dynamically, communicating via raw unix sockets rather than external orchestrators.

Key engineering pillars include:

  • PTY Multiplexing & WebSockets: Instead of executing commands inside a mock sandbox console, TempDev leverages a real pseudo-terminal (PTY) in the container. The backend proxies terminal output to the client's browser (rendered via xterm.js) using WebSockets, syncing window resize metrics seamlessly.
  • Dynamic Cloudflare Tunnel Provisioning: Exposing ports inside isolated sandboxes to the open web is notoriously hard. TempDev wraps cloudflared. When a user runs a server inside their browser terminal (e.g., on port 8080), TempDev spawns a routing process dynamically to provide an HTTPS URL accessible worldwide in seconds.
  • SQLite-backed Lifecycle Scheduler: Container state, billing, and event logs are persisted in SQLite with WAL mode for concurrent access. An in-memory sync.Map serves as a hot cache for active environments, while a background goroutine enforces idle timeouts (15min), max lifetime (12h), and orphan cleanup on server restart.

Resource Constraints & Hardened Security

Running a service that allows arbitrary code execution on a free-tier server is a massive security challenge. To avoid resource exhaustion and server abuse, the sandbox utilizes aggressive kernel-level mitigation: 

docker run -d \
  --memory="512m" \
  --cpus="0.5" \
  --pids-limit=64 \
  --cap-add=NET_ADMIN \
  --security-opt=no-new-privileges \
  --add-host=aws-metadata:169.254.169.254 \
  tempdev:latest

The --security-opt=no-new-privileges flag prevents privilege escalation via setuid/setgid binaries. All interactive sessions (WebSocket shell and SSH) run as a non-root dev user (UID 1000) via docker exec -u dev. --cap-add=NET_ADMIN is granted solely to allow iptables rules in the entrypoint that block access to the AWS metadata endpoint (169.254.169.254), preventing SSRF-based credential theft.

Benchmark Results

The project includes a reproducible Go benchmark suite (go test -bench=.). Measured on an AMD Ryzen 7 8840HS with a cached Docker image:

  • Single container cold start: ~270ms
  • 20 concurrent containers: ~1.6s total (~80ms each when parallelized)
  • Container cleanup: ~170ms
  • sshd startup: ~90ms

Conclusion

TempDev solves a personal developer pain point. It proves that you don't need a heavy infrastructure stack or heavy enterprise budgets to build responsive, isolated developer tools. You can inspect the full implementation on GitHub: github.com/schallten/container-provider.
